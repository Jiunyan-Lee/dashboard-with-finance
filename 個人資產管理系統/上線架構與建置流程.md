# 個人資產管理系統：上線架構與建置流程

> 文件版本：2026-08-31  
> 正式建議方案：**Netlify + Supabase Auth + Supabase PostgreSQL + Row Level Security（RLS）**  
> 狀態：規劃文件；尚未進行帳號、資料庫或部署設定。

## 1. 架構結論

```
使用者瀏覽器
  └─ Netlify：網站、網域、HTTPS、Git 自動部署
       └─ Supabase
            ├─ Auth：email／密碼註冊、登入、驗證信、密碼重設
            └─ PostgreSQL：使用者資料、月度資料卡、賣出紀錄
                 └─ RLS：使用者只能存取 user_id = 自己 UID 的資料列
```

Google Sheets 不作為正式多使用者資料庫。它可保留為管理者匯出、人工報表或一次性資料分析來源。

這個架構的重點是：資料隔離由資料庫的 RLS 規則直接強制執行，而非只靠前端畫面或自行撰寫的中介 API。Supabase 官方建議將 RLS 與 Auth 搭配使用，作為瀏覽器到資料庫的端到端保護。[RLS 官方文件](https://supabase.com/docs/guides/database/postgres/row-level-security)

## 2. 元件責任

| 元件 | 責任 | 不應負責 |
| --- | --- | --- |
| Netlify | 靜態前端部署、自訂網域、HTTPS、Git 持續部署 | 儲存個人財務資料、保存管理者密鑰 |
| Supabase Auth | 註冊、登入、登出、Email 驗證、忘記密碼、登入 session | 財務統計畫面 |
| Supabase Database | 月度資料、賣出紀錄、使用者資料、審計紀錄 | 前端介面呈現 |
| RLS | 限制登入者只可讀寫自己的資料 | 取代前端格式驗證 |
| 現有前端 | GUI、統計公式、圖表、資料卡、JSON 匯入／匯出 | 保存 `service_role` 金鑰 |
| Google Sheets（選用） | 管理報表、離線分析、匯出結果 | 正式即時資料庫 |

## 3. 資料模型

第一版建議使用三張核心資料表。

### profiles

| 欄位 | 說明 |
| --- | --- |
| `id` | UUID，對應 `auth.users.id` |
| `display_name` | 顯示名稱 |
| `created_at` | 建立時間 |
| `status` | 啟用／停用或邀請狀態 |

### monthly_snapshots

| 欄位 | 說明 |
| --- | --- |
| `id` | UUID |
| `user_id` | 使用者 UID，對應 `auth.users.id` |
| `month` | 資料月份，格式 `YYYY-MM` |
| `entry_date` | 當月資料填寫日期 |
| `salary` | 當月薪水 |
| `total_investment` | 當月總投入金額 |
| `payload` | JSONB：銀行帳戶、證券資產、證券戶現金、債務等完整資料 |
| `created_at`／`updated_at` | 建立與更新時間 |

唯一條件：`UNIQUE (user_id, month)`。  
因此同一位使用者再次寫入相同月份時，可明確選擇覆蓋或略過。

### trades

| 欄位 | 說明 |
| --- | --- |
| `id` | UUID（匯入舊資料時由系統補發） |
| `user_id` | 使用者 UID |
| `trade_date` | 賣出日期 |
| `name` | 標的名稱 |
| `cost` | 買進金額 |
| `proceeds` | 賣出金額 |
| `payload` | JSONB：保留未來擴充欄位與舊資料欄位 |
| `created_at`／`updated_at` | 建立與更新時間 |

使用 JSONB 保留現有單機版資料結構，可降低遷移風險；日後若需要更深入查詢，再逐步把常用欄位正規化。

## 4. 權限與安全設計

所有公開給前端的資料表都必須啟用 RLS，並至少設定 select、insert、update、delete 四類規則。

概念範例：

```sql
-- monthly_snapshots：使用者僅能操作自己的資料
create policy "Users read own monthly snapshots"
on public.monthly_snapshots for select
to authenticated
using ((select auth.uid()) = user_id);

create policy "Users insert own monthly snapshots"
on public.monthly_snapshots for insert
to authenticated
with check ((select auth.uid()) = user_id);

create policy "Users update own monthly snapshots"
on public.monthly_snapshots for update
to authenticated
using ((select auth.uid()) = user_id)
with check ((select auth.uid()) = user_id);

create policy "Users delete own monthly snapshots"
on public.monthly_snapshots for delete
to authenticated
using ((select auth.uid()) = user_id);
```

`trades` 與 `profiles` 也採相同原則。RLS 規則會在資料庫內執行，等同於每次查詢都自動加上只屬於該使用者的條件。[Supabase RLS 說明](https://supabase.com/docs/guides/database/postgres/row-level-security)

安全規則：

- 前端只使用 Supabase 的 publishable／anon key；這是可公開設定，但前提是 RLS 完整。
- **絕不可**將 `service_role` key、資料庫密碼或管理者權杖放入前端、Git 或 Netlify 公開環境變數。
- `service_role` 會繞過 RLS，只能放在可信任伺服器端工作，例如後續的管理腳本或 Edge Function。
- 使用 Email 驗證、密碼重設、登入轉址網域白名單。
- 以邀請制或白名單作為第一階段註冊方式。
- 寫入前仍需做前端資料格式檢查；RLS 保護權限，不能取代資料品質驗證。

## 5. 帳號流程

第一版採 Email／Password：

1. 親友填寫 email 與密碼註冊。
2. Supabase 寄送驗證信。
3. 驗證成功後可登入。
4. 登入後才載入其 `monthly_snapshots` 與 `trades`。
5. 忘記密碼時，Supabase 寄送重設信。
6. 管理者可用 `profiles.status` 或邀請名單限制未核准帳號。

Supabase 支援 email／password 註冊、登入與密碼重設。[Auth 文件](https://supabase.com/docs/guides/auth)

## 6. 既有單機 JSON 的匯入

可以匯入，但不直接把 JSON 當作雲端資料庫檔案讀取。

正確流程：

1. 使用者先登入自己的帳號。
2. 選擇單機版匯出的 JSON 檔。
3. 前端解析並驗證 `schemaVersion`、`snapshots`、`trades` 與必要欄位。
4. 顯示匯入預覽：
   - 月度資料卡筆數與月份區間
   - 賣出紀錄筆數
   - 重複月份與重複交易
   - 統計結果的預估差異
5. 使用者選擇：
   - 同月份覆蓋
   - 僅匯入不存在的月份
   - 取消
6. 系統將每筆資料寫入目前登入者的 `user_id` 範圍。
7. 顯示成功、略過、失敗筆數。
8. 保留原始 JSON 於使用者本機，絕不自動刪除。

舊版已移除的交易欄位可暫存於 `payload`／`metadata`，避免歷史資料遺失。

## 7. 前端改造範圍

保留目前的 GUI、計算公式、月度資料卡、熱力圖與圖表。主要調整資料存取：

| 現況 | 雲端版 |
| --- | --- |
| `localStorage` | Supabase Database |
| 本機資料載入 | 登入後查詢該使用者資料 |
| 本機儲存 | 依月份 upsert 月度資料、依 UUID 寫入交易 |
| JSON 匯入／匯出 | 登入後匯入、可隨時匯出自己的雲端備份 |
| 無帳號 | 註冊、登入、登出、忘記密碼、驗證提示 |

實作時建議先抽出 `Repository` 資料存取層：

- `LocalStorageRepository`：保留單機相容模式。
- `SupabaseRepository`：正式雲端讀寫。
- `ImportService`：JSON 驗證、預覽、衝突處理與批次寫入。

如此能在不改動統計與 UI 邏輯的前提下，逐步替換資料來源。

## 8. 分階段建置順序

### 第一階段：資料與程式準備

1. 將現有程式放入 Git 儲存庫。
2. 清除 Git 中的真實財務 JSON、帳密與私密設定。
3. 固定 JSON 匯出格式與 `schemaVersion`。
4. 抽出 LocalStorageRepository。
5. 建立匿名測試資料集。

### 第二階段：Supabase 資料庫與 RLS

1. 建立 Supabase 專案。
2. 建立 `profiles`、`monthly_snapshots`、`trades`。
3. 建立 `UNIQUE (user_id, month)`。
4. 啟用 RLS、設定 grants 與四種 CRUD policy。
5. 建立測試帳號 A 與 B。
6. 驗證 A 無法讀取、修改或刪除 B 的資料。

### 第三階段：登入與雲端同步

1. 啟用 Email／Password、Email 驗證與忘記密碼。
2. 製作註冊、登入、登出與重設密碼畫面。
3. 登入後才載入雲端資料。
4. 實作 SupabaseRepository。
5. 顯示同步中、已儲存、失敗與重試狀態。

### 第四階段：JSON 匯入／匯出

1. 建立登入後的匯入精靈。
2. 驗證格式與提供預覽。
3. 完成覆蓋／略過衝突策略。
4. 建立交易 UUID 與去重邏輯。
5. 使用自己的完整備份匯入，逐項核對統計、圖表與交易損益。
6. 保留一鍵匯出作為個人備份。

### 第五階段：Netlify 與試用

1. 將 Git 儲存庫連接 Netlify。
2. 建立 Deploy Preview 與正式分支部署。
3. 設定自訂網域與 HTTPS。
4. 在 Supabase Auth 設定正式網域的 Site URL 與 Redirect URL。
5. 以手機、桌機、帳號 A／B 測試登入、隔離、匯入、備份與密碼重設。
6. 先邀請 1–2 位親友試用，再逐步擴大。

Netlify 可連接 Git 儲存庫，在每次推送後自動部署網站。[Netlify 部署文件](https://docs.netlify.com/deploy/create-deploys/)

## 9. 上線前檢查清單

- [ ] 每張公開資料表都已啟用 RLS。
- [ ] 每張表皆有 select／insert／update／delete 的 allow 與 deny 測試。
- [ ] 前端沒有 `service_role`、資料庫密碼或任何管理者密鑰。
- [ ] 未登入者無法讀取資料。
- [ ] 帳號 A 完全無法存取帳號 B 的資料。
- [ ] 同月份匯入的覆蓋／略過策略已測試。
- [ ] 交易 UUID、去重與匯入結果統計已測試。
- [ ] 可正確匯出完整個人備份。
- [ ] Email 驗證與密碼重設的轉址網址為正式網域。
- [ ] 真實財務資料不在 Git、公開網址或測試環境。
- [ ] 已先以自身資料完整匯入並核對所有數值。

## 10. Google Sheets 的定位

Google Sheets 可保留，但用途改為：

- 管理者手動匯出與檢視報表。
- 個人年度摘要或投資分析。
- 資料庫外的第二份備份。
- 之後再透過受保護的管理端腳本或排程同步。

它不承擔使用者登入、權限隔離或即時交易資料庫的角色。
